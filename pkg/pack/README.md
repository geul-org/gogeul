# pack: 재개 가능한 스트림 쓰기

`pack.Stream`은 아주 큰 세트의 첫 세대를 한 번에 쓴다(위키데이터 1.2억 문서, 175 GB). 이 문서는 스트림이 마무리(`Close`) 중을 포함해 어느 순간에 멈춰도 이어 갈 수 있는 이유와, 마무리 중 메모리를 묶는 것을 적는다. 객체 형식은 geul-dev 설계 노트 `files/pack/README.md` §4·§6.1에 있고, 여기 내용은 형식의 어떤 바이트도 바꾸지 않는다.

## 약속

첫 `Checkpoint` 뒤 어느 시점에 프로세스를 죽이더라도, `ResumeStream`을 부르고 `Meta`가 말하는 나머지를 다시 넣고 `Close`를 부르면 끊김 없는 실행과 바이트까지 같은 세트가 나온다. 객체 이름이 내용 해시이므로 같은 객체를 다시 써도 해가 없다.

잃는 것은 마지막 저장 뒤의 작업뿐이다. 첫 `Checkpoint` 전에는 상태가 없으므로 호출자가 처음부터 다시 한다.

`Checkpoint` 없이 `Close`까지 간 작은 실행은 `Close`가 상태를 저장해도 호출자의 `Meta`가 비어 있다. wikigeul은 이 재개를 다른 실행으로 보고 거부하므로, 작업 폴더를 지우고 처음부터 한다.

## 멈춘 뒤 디스크에 있을 수 있는 것

`.stream/state`는 rename 한 번으로 바뀌므로 언제나 온전한 저장이다. 나머지는 그보다 앞서 있을 수 있다.

| 디스크 상태 | 뜻 | `ResumeStream`의 처리 |
|---|---|---|
| part 파일이 저장된 길이보다 길다 | 저장 뒤에 쓴 바이트 | 저장된 길이로 자른다 |
| 상태에 없는 `run-*` | 저장 뒤에 흘리거나 합친 런 | 지운다 |
| `hheads`가 저장된 수보다 길다 | 저장 뒤에 쓴 잎 머리 | H 패스를 다시 열 때 자른다 |
| 상태가 모르는 `o/` 객체 | 저장 뒤에 봉인됨 | 그 앞부분이 열린 객체일 수 있다(아래) |
| `.tmp-*`(세트 폴더, `m/`) | `writeFileSync` 도중에 죽음 | 지운다 |
| part 파일이 다른 객체를 담고 있다 | 열린 객체가 봉인되고 다음 객체가 같은 part 이름으로 시작됨 | 내용 확인에서 걸러지고 잘리지 않는다 |

마지막 줄이 옛 코드가 보지 못한 실패다. `data.part`·`index.part`는 이름이 고정이라 봉인 뒤의 part 파일은 다음 객체일 수 있고, 이것을 저장된 길이로 자르면 세트가 조용히 망가진다.

## 열린 객체 찾기

상태는 객체가 `Off` 바이트까지 열려 있었다고 말한다. `findPart`는 그 바이트를 두 곳에서 찾는다.

1. 상태가 닫지 않은, 종류가 같은 `o/`의 객체. 맞으면 part 파일로 복사해 되살린다(`restorePart`). 봉인된 객체는 그대로 둔다.
2. part 파일.

헤더 뒤부터 `Off`까지의 바이트가 체크포인트에 저장된 SHA-256 상태 `streamOpen.Sum`과 같으면 맞는 것이다. 해시는 객체를 쓰면서 이어 계산하고, 재개 뒤에도 남은 바이트에서 이어 간다. 비용은 데이터 전체에 SHA-256 한 번이다. 어느 쪽도 맞지 않으면 `ErrCorrupt`다. 정체를 확인할 수 없는 바이트에서는 이어 가지 않는다.

`Sum`이 생기기 전의 체크포인트는 구조로 확인한다.

- 색인 객체는 머리가 그 객체를 가리키는 P 잎들을 헤더 뒤부터 빈틈없이 담아야 한다(`Close` 전에는 색인 객체에 P 잎만 들어간다).
- 봉인된 데이터 pack은 인벤토리가 체크포인트의 항목·경로로 시작하고 다음 항목이 `Off`에서 시작해야 한다.
- 데이터 part 파일은 옛 코드처럼 그대로 받는다. 봉인된 객체를 먼저 보므로, 객체가 봉인된 경우라면 다음 객체를 담은 part가 여기까지 오지 않는다.

## 단계별 마무리

`Close`는 단계마다 `streamState.Close`에 저장한다.

| Phase | 저장 시점의 상태 | 재개한 `Close`가 할 일 |
|---|---|---|
| `closeStarted` | 레코드가 모두 들어옴, H 키를 흘림, 열린 객체 sync | 데이터 pack 봉인부터 |
| `closePDone` | 마지막 데이터 pack 봉인, P 층을 상태에 보관 | 런 합치기를 이어서 |
| `closeHPass` | 런을 줄임, H 패스 위치를 `saveLeaves` 잎마다 저장 | 가져간 항목 뒤에서 런을 다시 연다 |
| `closeHDone` | H 층을 상태에 보관 | 마지막 색인 객체 봉인, 매니페스트 |

`closeStarted` 뒤의 상태는 모든 레코드를 담지만 호출자의 `Meta`는 마지막 `Checkpoint` 것이고, 이를 모르는 호출자는 꼬리를 다시 넣는다. 그래서 마무리 중인 스트림의 `Put`·`PutNamed`는 마지막 키까지를 저장 없이 받고, `Encode`는 레코드를 압축하지 않으며, `Checkpoint`는 `Meta`만 저장한다. 기존 호출자는 코드를 바꾸지 않아도 재개된다. 마지막 키 뒤의 키는 오류다.

매니페스트와 `latest.txt`는 저장된 상태로만 정해지므로, 둘 사이나 작업 폴더 제거 전에 멈추면 그 쓰기만 되풀이한다.

## 마무리 중 메모리

| 쓰는 것 | 상한 |
|---|---|
| 합치기 읽기 버퍼 | `MergeRuns` × 1 MiB(기본 64 MiB), 런 수와 무관 |
| 합친 런·`hheads` 쓰기 버퍼 | 각 1 MiB |
| 블록 압축 | 인코더 하나. `closeCodec`이 레코드용 인코더를 버리고(`DefaultWorkers` 주석 기준 사전 인코더 하나 약 250 MB) `debug.FreeOSMemory`로 돌려준다. `EncodeAll` 출력은 인코더 수와 무관하다 |
| H 잎 머리 | 디스크(`hheads`). 메모리에는 max(`HRoot`, `HFanout`)개까지(`HRoot` 0이면 전부) |
| 첫 층 위의 H 내부 층 | `HLeaf` × `HFanout` 키당 머리 하나 |
| P 뿌리 | `PLeaf` 레코드당 머리 하나, 전부 메모리. 형식이 뿌리 블록 하나에 담으므로 이것만 문서 수에 비례한다(1.2억 문서에 약 1.5만 개) |
| 열린 데이터 pack 인벤토리 | `PackSize`로 묶임 |

측정: `TestStreamCloseMemory`의 힙 최고치는 런 100개·1000개에서 약 74·78 MiB, `MergeRuns` 8에서 약 11 MiB다(옛 코드는 런당 1 MiB). 위키데이터 복구 실행(런 1,220개)의 `Close` 구간 RSS는 1분 표본으로 254–360 MB였다. 죽은 실행은 4.7 GB였다.

합치는 순서는 출력을 바꾸지 않는다. `hEntryLess`가 전순서이고, 같은 키는 마지막 패스에서만 정리한다.

조절 손잡이는 세 가지다.

- `StreamOptions.MergeRuns`: 합치기 폭의 위 한도다. 합쳐진 런은 세트가 끝날 때까지 `Spent`로 디스크에 남으므로 런 한 벌만큼 디스크를 더 쓴다.
- `StreamOptions.MergeWidth`: 합치기마다 폭을 묻는다(2…`MergeRuns`로 자른다). 호출자가 메모리 예산에 맞춘 폭을 준다. 한 입력이 드는 메모리는 `MergeRunMemory`다. 폭이 좁으면 패스가 늘어 디스크와 시간을 더 쓰지만 출력은 같다.
- `Zstd.SetWorkers`: 레코드를 넣는 동안 인코더 수를 바꾼다. 인코더는 차례로 쓰이므로 활성 작업자만 줄여서는 메모리가 줄지 않는다. 출력은 같다.

## 마무리 멈추기

`Close`는 메모리를 스스로 재지 않는다. 대신 `StreamOptions.Pace`가 안전 지점마다 불린다. gogeul은 누가 왜 멈추는지 모른다.

| phase | 불리는 곳 | 멈출 때 잃는 것 |
|---|---|---|
| `close:data` | 마지막 데이터 pack 저장 뒤 | 없음 |
| `close:p` | P 층 저장 뒤 | 없음 |
| `close:merge` | 합치기마다, 합치기 안에서 `paceEntries` 항목마다 | 그 합치기 한 번(쓰던 런은 `ResumeStream`이 지운다) |
| `close:h` | H 잎을 쓸 때마다 | 없음(`hSave`로 위치를 저장하고 돌아온다) |
| `close:tree` | 첫 내부 층의 묶음마다 | 마지막 저장 뒤의 잎과 묶음(`saveLeaves` 잎 이내) |
| `close:index` | H 층 저장 뒤 | 없음 |

`Pace`가 오류를 돌려주면 `Close`는 `ErrStopped`이면서 그 오류인 값을 돌려준다(`errors.Is`·`errors.As` 둘 다 된다). `ResumeStream`과 `Close`를 다시 부르면 이어지고 같은 바이트가 나온다. `Pace`는 막아 둘 수도 있다.

호출자의 `Meta`는 `Close` 전에 마지막으로 저장한 값이다. 재개할 때 모든 레코드가 들어갔음을 알려면 `Close` 직전에 `Checkpoint`를 한 번 부른다.

## 출처로 읽기

`pkg/resolve`가 이 패키지를 import한다. 반대 방향은 없다. `GEULPROXY`의 `file://`와 `https://`는 `resolve`가 `Open`과 `FileStore`·`HTTPStore`로 세트를 직접 열고, 세트가 있는지는 `latest.txt`로만 판별한다(`pkg/resolve` README "저장 형태 판별"). 같은 `Reader`가 무압축 세트와 zstd 세트를 읽으므로 형태를 구별하지 않는다.

- `ErrNotFound`·`ErrVerify`는 이 패키지가 정의하고 `resolve.ErrNotFound`·`resolve.ErrVerify`는 같은 값이다.
- `Open`의 `ErrNotFound`는 "여기에 세트가 없다"(`latest.txt`가 없거나 고정한 매니페스트가 없다)뿐이다. `latest.txt`가 가리키는 매니페스트가 없으면 `ErrCorrupt`다.
- `Archive`는 세트만 안다. 세트 옆의 낱개 파일은 `resolve.Dir{Root, Store}`가 읽는다.
